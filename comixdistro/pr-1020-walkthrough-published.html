Walkthrough
Part 1 — Admin returns a submitted report for revision new in this PR

The old wording framed this as “Reject report.” This PR reframes the whole action as “Request changes”: the distributor is expected to revise and resubmit, not start over.

  1. Sign in as .
  2. Open the admin Events list and open the Одеса Книги event (approved; its report is awaiting review).
    ✅ The event show page opens with a Report tab and — new — a Request changes tab (Ukrainian: “Доопрацювання”).
  3. On the Report tab, look at the action row beside the green Approve report & complete event button.
    ✅ A quiet grey text link reads “Something to change?” (uk: “Потрібні зміни?”). It is deliberately understated so “request changes” never looks like the default next to Approve.
  4. Click that “Something to change?” link.
    ✅ The Request changes tab activates, showing the heading “Return this report for revision”, an explanatory intro, and a note textarea with a hint that the distributor will see the note.
  5. Click Request changes (the yellow submit button) without typing a note.
    ✅ Inline validation blocks the submit and asks for a note of at least 10 characters — no request is sent.
  6. Type a real note, e.g. and click Request changes. Confirm the dialog.
    ✅ Redirect back to the event with a success flash: “Report was returned to the distributor for revision.” The report is no longer marked submitted.
Part 2 — Distributor sees the banner and revises new in this PR

The returned report now surfaces as a prominent amber banner that links straight to the edit form — in three places, all consistent.

  1. Sign out, then sign in as (Odesa). Land on the home page.
    ✅ An amber “returned for revision” banner sits above the event card (not buried at its foot), with a white Revise report button. The card itself shows no “finish report” prompt — a returned report is not mistaken for an unfinished draft.
  2. Open the event’s own page (from the card).
    ✅ The same amber pointer banner with the Revise report button appears — visually identical to the home page.
  3. Click Revise report.
    ✅ You land on the report edit form, and the admin’s note is shown at the top in a labeled white card so you can see exactly what to change while editing.
  4. Open the report’s show page as well (e.g. via the report link).
    ✅ The full banner with the note appears, plus a “Revise report” link (shown because you’re allowed to edit).
  5. Edit the narrative / add what was asked, then submit the report.
    ✅ The report is submitted again; the amber banner and the admin’s note disappear (the note clears on resubmission). The event returns to “awaiting review”.
Part 3 — The notification email new in this PR

Requesting changes emails the distributor. The link now points to the report’s view page (not a bare edit link), matching the “review, then revise” framing.

  1. After completing Part 1, switch to the browser tab letter_opener opened (or re-trigger by requesting changes again).
    ✅ Subject: “Report returned for revision: <event title>”. Body includes the admin’s note under a “Reason” heading and a “View report” link.
  2. Hover/inspect the “View report” link.
    ✅ It points at the report show page (/events/<id>/event_report), not the /edit URL.
Not browser-testable
  • The column rename migration (rejection_reason → revision_note) — a schema change with no direct UI; it’s exercised implicitly by every step above and covered by the model/controller tests.
  • Co-occurring validation errors — e.g. requesting changes while the report is independently invalid surfaces the specific error rather than the generic “provide a note” message. This is gated behind a valid UI so it’s covered by controller tests, not reachable by hand.
  • “No submitted report” guard — the action refuses if there’s nothing submitted to return; only reachable via a crafted request, covered by tests.
