A quick browser exercise of the issue #644 fix. A corrupt “ghost” photo — a file that claims image/jpeg but whose bytes libvips can’t decode — used to slip through upload and then 500 the report page when Active Storage generated a display variant. This PR closes both ends:

⛔
Reject on upload — saving/submitting a report with an undecodable photo now fails validation with a clear message, so bad bytes never get stored.
🖼️
Graceful display fallback — any blob the ingest optimizer flags as undecodable (a corrupt upload that slipped past the gate before this fix) now renders a placeholder card instead of crashing the page, everywhere report photos appear: distributor report, distributor edit form, and admin event page.

Part 2 — Distributor: an undecodable photo shows a placeholder, not a crash new in this PR

Because Part 1 now blocks corrupt uploads, the only way a stored blob becomes undecodable is the ingest optimizer flagging one that pre-dates this fix. Simulate that flag in the console (this mirrors exactly what OptimizeEventReportPhotosJob does). Open and run:

report = EventReport.all.select { |r| r.photos.attached? }.max_by(&:created_at)
report.photos.first.blob.then { |b| b.update!(metadata: b.metadata.merge("undecodable" => true)) }
report.event.distributor.users.pluck(:email) # confirm this is olena's distributor

Not browser-testable
The ingest optimizer (OptimizeEventReportPhotosJob) re-probing a failed photo and marking it undecodable (vs. leaving a transient storage failure alone for retry) runs in a background job — covered by job tests. Parts 2–3 simulate its output via the metadata flag.
EventReport.blob_decodable? treating a storage read failure (transient 5xx/timeout or checksum mismatch) as “decodable” so it never 500s report submission — covered by a model test; not reliably reproducible in the browser.
The job skipping re-decode/re-report for an already-flagged blob on re-enqueue — job test.
